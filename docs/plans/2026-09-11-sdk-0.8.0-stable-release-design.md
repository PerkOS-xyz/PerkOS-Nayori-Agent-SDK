# Diseño de release estable `@perkos/agent-sdk@0.8.0`

## Objetivo y decisión

Promover como `0.8.0` estable el árbol exacto que pasó QA, el E2E privado `u18`, los gates de
distribución y el rollout productivo coordinado. No se cambia lógica, contratos, custodia, límites
de firma ni defaults de red. La alternativa de mantener `0.8.0-rc.2` bajo `next` dejaría fuera las
mejoras posteriores de discovery y evidencia privada; publicar otra prerelease repetiría un gate ya
cerrado. Por eso el release estable es la opción mínima y verificable.

El PR actualiza versión de paquete/lockfile, versión anunciada por MCP, manuales activos,
quickstart, pruebas de distribución y release notes. El changelog preserva intactas las entradas
históricas de `rc.1` y `rc.2`. La documentación distinguirá con precisión tres estados: código
preparado en el PR, publicación npm posterior al merge humano y evidencia operativa interna que no
cuenta como adopción externa.

## Gate y publicación

Antes del merge: `npm ci`, typecheck, 414 pruebas, build, audit de severidad alta y
`npm pack --dry-run`. Después del merge, la publicación se ejecuta exclusivamente desde esta Mac
con el commit exacto de `main`; no se usa GitHub Actions. Se verifica versión, integrity y contenido
instalando desde el registry en un directorio limpio. Sólo entonces se mueve `latest` a `0.8.0` y se
actualiza el portal de documentación con el estado publicado.

El demo usa el paquete público, dos procesos/roles separados y sBTC. Expone registro, discovery,
creación, funding, asignación, entrega, evaluación, apelación opcional, settlement y lectura de
reputación. Las llaves permanecen en archivos externos mode 0600; el video y sus recibos se guardan
fuera de Git. Las wallets controladas se etiquetan `internal-team-operated-not-m2-adoption`.
